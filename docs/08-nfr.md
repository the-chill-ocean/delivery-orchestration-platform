# Нефункциональные требования

Ниже приведены целевые значения, принятые как проектные допущения для System Design.

Они не основаны на статистике реального маркетплейса и должны быть уточнены по результатам анализа production-нагрузки и нагрузочного тестирования.

---

## 1. Нагрузочный профиль

Приняты следующие проектные допущения:

| Показатель | Целевое значение |
|---|---:|
| Средняя нагрузка на `POST /delivery-offers` | 300 RPS |
| Пиковая нагрузка на `POST /delivery-offers` | 800 RPS |
| Пиковая нагрузка на `GET /deliveries/{deliveryId}` | 1500 RPS |
| Входящие события Kafka | до 1000 сообщений/сек |
| Максимальный кратковременный рост нагрузки | x3 от средней |

Система должна масштабироваться горизонтально без изменения API-контрактов и бизнес-логики.

---

## 2. Время ответа API

### POST /delivery-offers

Так как операция зависит от нескольких внешних Carrier API:

| Метрика | Целевое значение |
|---|---:|
| p95 | ≤ 2 сек |
| p99 | ≤ 4 сек |

Если отдельный Carrier не отвечает в установленный timeout, платформа не должна бесконечно ожидать его ответ.

---

### POST /delivery-offers/{offerId}/validate

| Метрика | Целевое значение |
|---|---:|
| p95 | ≤ 1.5 сек |
| p99 | ≤ 3 сек |

---

### GET /deliveries/{deliveryId}

| Метрика | Целевое значение |
|---|---:|
| p95 | ≤ 200 мс |
| p99 | ≤ 500 мс |

---

### POST /deliveries/{deliveryId}/cancel

Время выполнения операции зависит от текущего состояния Delivery.

| Сценарий | Требование |
|---|---|
| Отмена в статусе `CREATED` без обращения к Carrier | p95 ≤ 500 мс |
| Отмена в статусе `ACCEPTED` | Время зависит от ответа Carrier; целевое значение определяется отдельно |

Для Delivery в статусе `ACCEPTED` платформа отправляет запрос на отмену во внешнюю систему перевозчика.

Статус `CANCELLED` устанавливается только после подтверждения отмены со стороны Carrier.

Если ответ Carrier не получен из-за timeout, платформа не должна считать доставку отменённой. Необходимо проверить фактический результат операции.
---

## 3. Доступность

Целевая доступность Delivery Orchestration Platform:

```text
99.9% в месяц
```

Недоступность одного Carrier не считается недоступностью всей платформы, если доставка может быть рассчитана или выполнена через других перевозчиков.

---

## 4. Обработка событий

Для `OrderReadyForDelivery`:

| Требование | Целевое значение |
|---|---:|
| Время до начала обработки события, p95 | ≤ 5 сек |
| Kafka consumer lag в штатном режиме | ≤ 30 сек |
| Потеря подтверждённого события | недопустима |

Повторная доставка Kafka-события допускается.

Consumer должен обеспечивать идемпотентную обработку.

---

## 5. Создание Delivery

После получения `OrderReadyForDelivery`:

```text
Delivery должна быть создана в БД не позднее 5 секунд
```

для 95% событий при штатной работе системы.

Время получения подтверждения от Carrier измеряется отдельно, так как зависит от внешней системы.

---

## 6. Отказоустойчивость внешних интеграций

Для запросов к Carrier должны использоваться:

```text
timeout
retry
exponential backoff
circuit breaker
```

Retry выполняется только для временных технических ошибок:

```text
timeout
HTTP 429
HTTP 5xx
network error
```

Бизнес-ошибки Carrier не должны автоматически повторяться.

Недоступность одного Carrier не должна блокировать работу с другими перевозчиками.

---

## 7. Надёжность обработки данных

Система должна обеспечивать:

```text
at-least-once delivery
```

для Kafka-событий.

Повторное получение:

```text
OrderReadyForDelivery
```

не должно создавать дополнительную активную Delivery для того же Shipment.

Для критичных изменений состояния Delivery используется Transactional Outbox.

---

## 8. Восстановление после сбоя

Проектные цели:

| Метрика | Значение |
|---|---:|
| RTO | ≤ 30 минут |
| RPO | ≤ 5 минут |

Для данных Delivery и DeliveryAttempt потеря уже подтверждённых бизнес-операций должна быть минимизирована использованием транзакций и резервного копирования БД.

---

## 9. Безопасность

Внутренние API должны использовать:

```text
TLS 1.2+
```

Для service-to-service authentication предполагается:

```text
OAuth 2.0 Client Credentials
```

или эквивалентный механизм, принятый инфраструктурной платформой.

Все endpoint должны требовать аутентификацию, кроме технических health-check endpoint, доступ к которым ограничивается инфраструктурным контуром.

Webhook Carrier должен проходить проверку подлинности через поддерживаемый Carrier механизм:

```text
HMAC signature
mTLS
secret token
```

---

## 10. Логирование

Каждая операция должна содержать correlation identifiers:

```text
requestId
correlationId
eventId
deliveryId
deliveryAttemptId
shipmentId
```

Логи технических операций должны быть доступны минимум:

```text
30 дней
```

Секреты, access token и чувствительные пользовательские данные не должны попадать в application logs.

---

## 11. Мониторинг

Обязательные технические метрики:

| Метрика | Назначение |
|---|---|
| API p95 / p99 latency | Контроль деградации API |
| HTTP 5xx rate | Контроль ошибок платформы |
| Carrier timeout rate | Контроль состояния внешних интеграций |
| Kafka consumer lag | Контроль задержки обработки событий |
| DLQ size | Обнаружение необработанных событий |
| Retry rate | Обнаружение нестабильных зависимостей |
| Outbox backlog | Контроль публикации событий |
| DeliveryAttempt failure rate | Контроль ошибок доставки |

Метрики Carrier должны агрегироваться отдельно по `carrierId`.

---

## 12. Алерты

Минимально должны существовать алерты на:

```text
API 5xx rate выше допустимого порога
p95 latency выше SLO
Kafka consumer lag > 30 секунд
появление сообщений в DLQ
рост outbox backlog
массовые timeout одного Carrier
резкий рост failed DeliveryAttempt
```

Точные alert thresholds для процентных метрик определяются после получения baseline production-нагрузки.

---

## 13. Масштабирование

Delivery Orchestration Platform должна быть stateless на уровне экземпляров приложения.

```text
                    Load Balancer
                         |
             +-----------+-----------+
             |           |           |
           DOP #1      DOP #2      DOP #3
             |           |           |
             +-----------+-----------+
                         |
                  Database / Kafka
```

Добавление нового экземпляра приложения должно увеличивать доступную вычислительную мощность без изменения бизнес-логики.

Kafka consumers масштабируются через consumer group.

Максимальное эффективное количество параллельных consumers ограничивается количеством partitions соответствующего topic.
