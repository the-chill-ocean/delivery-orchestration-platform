# Надёжность и обработка сбоев

Документ описывает подходы Delivery Orchestration Platform к обработке повторных сообщений, временных ошибок, недоступности Carrier и частичных сбоев.

Основные механизмы:

- idempotency;
- retry;
- timeout;
- DLQ;
- защита от дублирования;
- Outbox Pattern;
- проверка допустимости переходов состояний;
- переключение между Carrier.

---

# 1. Модель доставки сообщений

Для взаимодействия через Kafka предполагается модель:

```text
at-least-once delivery
```

Это означает, что одно и то же событие может быть доставлено consumer более одного раза.

Например:

```text
OrderReadyForDelivery
OrderReadyForDelivery
```

Повторное получение события не должно приводить к созданию второй Delivery.

Поэтому consumers должны обрабатывать сообщения идемпотентно.

---

# 2. Идемпотентная обработка Kafka-событий

Каждое событие содержит уникальный `eventId`.

Для предотвращения повторной обработки используется таблица `processed_events` с уникальным ограничением по `eventId`.

### Алгоритм обработки

При получении `OrderReadyForDelivery` платформа выполняет следующие действия:

1. Начинает транзакцию БД.
2. Пытается зарегистрировать `eventId` в таблице `processed_events`.
3. Если `eventId` уже существует, завершает обработку без повторного выполнения бизнес-операции.
4. Проверяет, существует ли `Delivery` для указанного `shipmentId`.
5. Если `Delivery` ещё не существует, создаёт её и записывает `DeliveryCreated` в таблицу Outbox.
6. Фиксирует транзакцию.
7. После успешного commit подтверждает обработку Kafka-сообщения.

Регистрация `eventId`, создание `Delivery` и запись в Outbox выполняются атомарно в рамках одной транзакции БД.

Если транзакция завершилась ошибкой, все её изменения откатываются, а Kafka-сообщение остаётся доступным для повторной обработки.

### Дополнительная защита

Уникальности `eventId` недостаточно, поскольку два различных события могут относиться к одному `shipmentId`.

Поэтому на уровне БД дополнительно обеспечивается бизнес-инвариант:

Один Shipment может иметь не более одной Delivery.

Конкурентное создание Delivery предотвращается уникальным ограничением по `shipmentId`.

### Внешние вызовы

Транзакция БД не должна оставаться открытой во время обращения к Carrier API.

Взаимодействие с перевозчиком выполняется отдельно после фиксации внутреннего состояния. Создание доставки у Carrier защищается собственной идемпотентностью по `deliveryAttemptId`.

Таким образом, атомарность локальных изменений не означает атомарности распределённой операции с внешним Carrier.

---

# 3. Защита от создания двух Delivery

Защита только по `eventId` недостаточна.

Теоретически Order Service может опубликовать два разных события:

```text
eventId = evt-1
shipmentId = shp-501
```

и:

```text
eventId = evt-2
shipmentId = shp-501
```

Оба события различаются, но относятся к одному Shipment.

Поэтому на уровне данных дополнительно должна существовать бизнес-гарантия:

```text
один Shipment → не более одной активной Delivery
```

Для этого может использоваться уникальное ограничение на уровне БД.

Таким образом защита строится в два уровня:

```text
eventId
    ↓
защита от повторной доставки одного события

shipmentId
    ↓
защита бизнес-инварианта
```

---

# 4. Идемпотентность при создании доставки у Carrier

Особенно опасен следующий сценарий:

```text
Delivery Orchestration
        |
        | POST create delivery
        v
Carrier
```

Carrier создал доставку, но ответ потерялся из-за timeout.

Delivery Orchestration видит ошибку:

```text
TIMEOUT
```

При простом повторении POST Carrier может создать вторую доставку.

Поэтому операция создания доставки должна быть идемпотентной.

### Предпочтительный вариант

Delivery Orchestration передаёт Carrier уникальный ключ операции:

```text
Idempotency-Key: deliveryAttemptId
```

Например:

```text
Idempotency-Key: attempt-1001
```

При повторном запросе с тем же ключом Carrier должен вернуть результат уже выполненной операции, а не создавать новую доставку.

---

## Если Carrier не поддерживает Idempotency-Key

Платформа должна передавать собственный уникальный идентификатор операции, например:

```text
clientRequestId = deliveryAttemptId
```

Перед повторным созданием Delivery Orchestration пытается проверить, существует ли уже доставка с таким идентификатором.

Если определить результат предыдущего вызова невозможно, запрос не должен бесконечно повторяться вслепую.

Такая ситуация требует reconciliation или ручного разбора.

---

# 5. Timeout

Все синхронные вызовы внешних Carrier API должны иметь ограничение времени ожидания.

Платформа не должна бесконечно ожидать ответ внешнего сервиса.

Высокоуровнево:

```text
Delivery Orchestration
        |
        | request
        v
Carrier
        |
      timeout
        |
        v
обработка временной ошибки
```

Конкретные значения timeout определяются на основании:

- SLA Carrier;
- допустимого времени ответа пользовательского сценария;
- статистики реальных задержек.

Фиксированное значение timeout в рамках текущего System Design не задаётся.

---

# 6. Retry

Retry используется только для ошибок, которые потенциально могут исчезнуть при повторной попытке.

### Retry возможен для

```text
timeout
HTTP 429 Too Many Requests
HTTP 5xx
временная недоступность сети
```

### Retry не выполняется для

```text
400 Bad Request
некорректного адреса
превышения допустимого веса
неподдерживаемого типа груза
других бизнес-ограничений Carrier
```

Повтор одного и того же некорректного запроса не изменит результат.

---

# 7. Retry policy

Повторные запросы не должны выполняться сразу один за другим.

Используется:

```text
exponential backoff
```

Например:

```text
первая ошибка
    ↓
небольшая задержка
    ↓
retry
    ↓
увеличенная задержка
    ↓
retry
```

Для снижения риска одновременных повторных запросов от большого количества instances может использоваться:

```text
jitter
```

Конкретное количество попыток и интервалы определяются эксплуатационными требованиями и характеристиками конкретного Carrier.

---

# 8. DeliveryAttempt и ошибки Carrier

Каждая попытка создания доставки у конкретного Carrier хранится отдельно в:

```text
DeliveryAttempt
```

Пример:

```text
Delivery
   |
   +-- DeliveryAttempt #1
   |      Carrier A
   |      FAILED
   |      TIMEOUT
   |
   +-- DeliveryAttempt #2
          Carrier B
          ACCEPTED
```

Это позволяет:

- не перезаписывать историю предыдущих попыток;
- сохранять `carrierDeliveryId` отдельно для каждого Carrier;
- анализировать причины отказов;
- переключаться между Carrier;
- выполнять аудит.

---

# 9. Переключение Carrier

Если текущий Carrier не смог принять доставку, Delivery Orchestration может создать новый `DeliveryAttempt`.

Пример:

```text
Delivery
    |
    v
DeliveryAttempt #1
Carrier A
FAILED
    |
    v
поиск альтернативы
    |
    v
DeliveryAttempt #2
Carrier B
ACCEPTED
```

Автоматическое переключение разрешено только если сохраняются согласованные с пользователем условия:

- тип доставки не изменяется;
- стоимость для пользователя не увеличивается;
- срок доставки остаётся в согласованном диапазоне;
- ограничения Shipment выполняются.

Если для продолжения необходимо изменить стоимость, срок или выбранный ПВЗ, автоматическое переключение не выполняется.

Требуется повторное подтверждение условий пользователем.

---

# 10. DLQ

Если Kafka-событие не удаётся успешно обработать после допустимого количества повторных попыток, оно помещается в:

```text
Dead Letter Queue
```

Например:

```text
delivery.order-ready.dlq
```

DLQ позволяет не блокировать обработку остальных событий из-за одного проблемного сообщения.

Для сообщения в DLQ необходимо сохранять как минимум:

| Поле | Описание |
|---|---|
| `eventId` | Идентификатор исходного события |
| `eventType` | Тип события |
| `payload` | Исходное сообщение |
| `failureReason` | Последняя причина ошибки |
| `retryCount` | Количество попыток обработки |
| `failedAt` | Время помещения сообщения в DLQ |

Сообщения из DLQ должны быть доступны для анализа и повторной обработки после устранения причины ошибки.

---

# 11. Ошибки при изменении статуса Delivery

Carrier может повторно отправить один и тот же webhook.

Например:

```text
IN_TRANSIT
IN_TRANSIT
```

Повторное сообщение не должно повторно изменять Delivery и генерировать лишние события.

Кроме того, внешние события могут прийти не в ожидаемом порядке.

Например:

```text
DELIVERED
```

а позже из-за задержки:

```text
IN_TRANSIT
```

Delivery Orchestration не должна выполнять переход:

```text
DELIVERED → IN_TRANSIT
```

если он запрещён внутренней state machine.

Перед изменением состояния платформа проверяет:

```text
currentStatus + incomingStatus
            ↓
      allowed transition?
```

Если переход недопустим, состояние Delivery не изменяется, а ситуация логируется для дальнейшего анализа.

---

# 12. Атомарность изменения БД и публикации события

Рассмотрим сценарий:

```text
Delivery.status = IN_TRANSIT
```

сохранён в БД, после чего платформа должна отправить:

```text
DeliveryStatusChanged
```

Возможен сбой:

```text
UPDATE Delivery
        ↓
успешно
        ↓
приложение падает
        ↓
Kafka event не опубликован
```

В результате БД и Kafka окажутся несогласованы.

Для решения используется:

```text
Transactional Outbox Pattern
```

---

# 13. Transactional Outbox

Изменение Delivery и создание записи для будущего события выполняются в одной локальной транзакции БД.

```text
BEGIN TRANSACTION

UPDATE Delivery
status = IN_TRANSIT

INSERT INTO outbox
DeliveryStatusChanged

COMMIT
```

После commit отдельный publisher отправляет запись из `outbox` в Kafka.

```text
Database
   |
   | outbox
   v
Outbox Publisher
   |
   v
Kafka
```

Если публикация не удалась, запись остаётся в outbox и может быть отправлена повторно.

Такой подход снижает риск ситуации:

```text
данные изменились,
но событие потерялось
```

Consumer при этом всё равно должен оставаться идемпотентным, потому что Outbox Publisher может отправить одно сообщение повторно.

---

# 14. Circuit Breaker

Если конкретный Carrier длительное время недоступен, бессмысленно продолжать отправлять ему каждый новый запрос.

Для защиты платформы может использоваться:

```text
Circuit Breaker
```

Упрощённо:

```text
Carrier работает
    ↓
CLOSED

много последовательных ошибок
    ↓
OPEN

запросы временно не отправляются
    ↓
через некоторое время
HALF_OPEN

тестовый запрос
    ↓
успешно → CLOSED
ошибка   → OPEN
```

Это позволяет быстрее исключить явно недоступного Carrier из текущего процесса выбора.

---

# 15. Частичная недоступность Carrier

Недоступность одного Carrier не должна автоматически означать недоступность всей Delivery Orchestration Platform.

Например:

```text
Carrier A → timeout
Carrier B → отвечает
Carrier C → отвечает
```

Если Carrier B и Carrier C могут выполнить доставку, платформа продолжает работу с доступными вариантами.

Если ни одного Carrier невозможно проверить из-за технической недоступности, операция может завершиться:

```text
503 Service Unavailable
```

Важно отличать:

```text
вариантов доставки нет
```

от:

```text
невозможно определить доступные варианты
```

---

# 16. Reconciliation

Для обнаружения рассинхронизаций может использоваться периодический reconciliation-процесс.

Например, он может находить Delivery, которые длительное время находятся в промежуточном состоянии:

```text
CREATED
ACCEPTED
IN_TRANSIT
```

и проверять их состояние у Carrier.

Reconciliation используется как дополнительный механизм восстановления, а не как основной способ получения статусов.

---

# 17. Основные сценарии отказа

| Сценарий | Решение |
|---|---|
| Kafka доставила событие повторно | Idempotency по `eventId` |
| Для одного Shipment пришли два разных события | Бизнес-инвариант и уникальное ограничение |
| Carrier временно недоступен | Timeout + Retry |
| Carrier долго недоступен | Circuit Breaker / другой Carrier |
| Carrier вернул бизнес-ошибку | Retry не выполняется |
| Carrier создал доставку, но ответ потерялся | Idempotency Key / проверка результата |
| Событие невозможно обработать | DLQ |
| Webhook пришёл повторно | Идемпотентная обработка |
| Статус Carrier пришёл не по порядку | Проверка state machine |
| БД обновлена, но событие Kafka не отправлено | Transactional Outbox |
| Состояние Delivery долго не меняется | Reconciliation |

---

# 18. Основные принципы

Delivery Orchestration Platform проектируется с учётом того, что:

```text
сообщения могут дублироваться;
сеть может быть недоступна;
ответ может потеряться;
Carrier может работать нестабильно;
события могут приходить с задержкой;
частичный сбой не должен приводить к потере состояния.
```

Поэтому система не полагается на гарантированное однократное выполнение операции.

Критичные операции проектируются как идемпотентные, а история попыток сохраняется в `DeliveryAttempt`.
