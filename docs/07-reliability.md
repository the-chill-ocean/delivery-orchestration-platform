# Надёжность и обработка сбоев

Документ описывает подходы Delivery Orchestration Platform к обработке повторных сообщений, временных ошибок, недоступности Carrier и частичных сбоев.

Основные механизмы:

- idempotency;
- retry;
- timeout;
- DLQ;
- защита от дублирования;
- Outbox Pattern;
- проверка допустимости переходов состояний;
- переключение между Carrier.

---

## 1. Модель доставки сообщений

Для взаимодействия через Kafka предполагается модель:

```text
at-least-once delivery
```

Это означает, что одно и то же событие может быть доставлено consumer более одного раза.

Например:

```text
OrderReadyForDelivery
OrderReadyForDelivery
```

Повторное получение события не должно приводить к созданию второй Delivery.

Поэтому consumers должны обрабатывать сообщения идемпотентно.

---
## 2. Основные принципы

Delivery Orchestration Platform проектируется с учётом того, что:

```text
сообщения могут дублироваться;
сеть может быть недоступна;
ответ может потеряться;
Carrier может работать нестабильно;
события могут приходить с задержкой;
частичный сбой не должен приводить к потере состояния.
```

Поэтому система не полагается на гарантированное однократное выполнение операции.

Критичные операции проектируются как идемпотентные, а история попыток сохраняется в `DeliveryAttempt`.
---

## 3. Идемпотентная обработка Kafka-событий

Каждое событие содержит уникальный `eventId`. Для защиты от повторной обработки используется таблица `processed_events` с уникальным ограничением по `eventId`.

### Алгоритм обработки OrderReadyForDelivery

При получении события платформа выполняет одну транзакцию БД:

1. Регистрирует `eventId` в таблице `processed_events`.
2. Если событие уже обработано, повторное выполнение бизнес-операции не производится.
3. Проверяет существование `Delivery` по `shipmentId`.
4. Если `Delivery` отсутствует:
   - создаёт `Delivery`;
   - записывает `DeliveryCreated` в Transactional Outbox;
   - создаёт внутреннее задание первоначального оформления со статусом `PENDING`.
5. Если `Delivery` уже существует:
   - не создаёт повторную `Delivery`;
   - не публикует повторно `DeliveryCreated`;
   - не создаёт дополнительное задание первоначального оформления;
   - проверяет соответствие `orderId` и продолжает использовать существующую Delivery.
6. Фиксирует транзакцию.

Повторное событие с новым `eventId`, но тем же `shipmentId`, регистрируется как обработанное, однако не должно повторно запускать первоначальное создание Delivery.

Существующая Delivery и ранее созданное задание продолжают обрабатываться независимо от повторного события.

После успешного commit платформа подтверждает обработку Kafka-сообщения.

Регистрация события, создание Delivery, запись в Outbox и создание задания выполняются атомарно. При ошибке транзакция откатывается целиком.

Уникальное ограничение на `Delivery.shipmentId` дополнительно предотвращает создание второй доставки при получении разных событий для одного Shipment.

### Надёжное продолжение процесса

Для гарантированного запуска оформления доставки используется техническая таблица `delivery_creation_jobs`.

| Поле | Описание |
|---|---|
| `jobId` | Уникальный идентификатор задания |
| `deliveryId` | Идентификатор Delivery |
| `jobType` | Тип задания: `INITIAL` или `ALTERNATIVE` |
| `deliveryOfferId` | Идентификатор предложения, на основании которого выполняется оформление |
| `status` | Состояние задания: `PENDING`, `IN_PROGRESS`, `COMPLETED`, `BLOCKED` |
| `leaseUntil` | Время окончания периода закрепления задания за обработчиком |
| `nextAttemptAt` | Время следующей допустимой попытки обработки |
| `createdAt` | Время создания задания |
| `updatedAt` | Время последнего изменения |

### Типы заданий

`INITIAL` — первоначальное оформление доставки после получения `OrderReadyForDelivery`.

`ALTERNATIVE` — повторное оформление доставки после получения `DeliveryAlternativeApproved`.

Для одной Delivery допускается не более одного задания первоначального оформления.

Для альтернативных предложений используется уникальность по комбинации `deliveryId`, `jobType` и `deliveryOfferId`. Повторное получение подтверждения одного и того же предложения не должно создавать дополнительное задание.

Задания обоих типов обрабатываются одним механизмом с учётом текущего состояния Delivery и существующих DeliveryAttempt.

Если результат предыдущего обращения к Carrier неизвестен, создание новой попытки запрещено до завершения reconciliation.

Фоновый обработчик получает задания из БД и запускает оформление доставки.

Последовательность:

1. Получает доступное задание и временно закрепляет его за собой.
2. Загружает Delivery, DeliveryOffer и snapshot Shipment.
3. Определяет подходящего Carrier.
4. Создаёт DeliveryAttempt со статусом `PENDING`.
5. Сохраняет DeliveryAttempt в БД.
6. Обращается к Carrier API вне транзакции БД.
7. После подтверждения Carrier сохраняет `carrierDeliveryId`, изменяет состояния DeliveryAttempt и Delivery, затем завершает задание.

Если приложение падает, незавершённое задание остаётся в БД. После истечения `leaseUntil` другой обработчик может продолжить его выполнение.

При возобновлении обработки платформа сначала проверяет существующий DeliveryAttempt и результат предыдущего обращения к Carrier. Она не должна автоматически создавать новую попытку, если результат предыдущей неизвестен.

Задание переводится в `COMPLETED` после успешного завершения оформления или в `BLOCKED`, если дальнейшая автоматическая обработка невозможна и требуется отдельный сценарий восстановления.

Повторный запуск задания не должен создавать дублирующие Delivery или DeliveryAttempt.

## 4. Защита от создания двух Delivery

Защита только по `eventId` недостаточна.

Теоретически Order Service может опубликовать два разных события:

```text
eventId = evt-1
shipmentId = shp-501
```

и:

```text
eventId = evt-2
shipmentId = shp-501
```

Оба события различаются, но относятся к одному Shipment.

Поэтому на уровне данных дополнительно должна существовать бизнес-гарантия:

```text
один Shipment → не более одной Delivery независимо от её текущего состояния
```

Для этого может использоваться уникальное ограничение на уровне БД.

Таким образом защита строится в два уровня:

```text
eventId
    ↓
защита от повторной доставки одного события

shipmentId
    ↓
защита бизнес-инварианта
```
Один Shipment может иметь не более одной Delivery независимо от её текущего состояния.

На уровне БД устанавливается уникальное ограничение на `Delivery.shipmentId`.

При смене Carrier новая Delivery не создаётся. Вместо этого создаётся новый `DeliveryAttempt`, связанный с существующей Delivery.

## 5. Идемпотентность при создании доставки у Carrier

Особенно опасен следующий сценарий:

```text
Delivery Orchestration
        |
        | POST create delivery
        v
Carrier
```

Carrier создал доставку, но ответ потерялся из-за timeout.

Delivery Orchestration видит ошибку:

```text
TIMEOUT
```

При простом повторении POST Carrier может создать вторую доставку.

Поэтому операция создания доставки должна быть идемпотентной.

### Предпочтительный вариант

Delivery Orchestration передаёт Carrier уникальный ключ операции:

```text
Idempotency-Key: deliveryAttemptId
```

Например:

```text
Idempotency-Key: attempt-1001
```

При повторном запросе с тем же ключом Carrier должен вернуть результат уже выполненной операции, а не создавать новую доставку.

---

### Если Carrier не поддерживает Idempotency-Key

Платформа должна передавать собственный уникальный идентификатор операции, например:

```text
clientRequestId = deliveryAttemptId
```

Перед повторным созданием Delivery Orchestration пытается проверить, существует ли уже доставка с таким идентификатором.

Если определить результат предыдущего вызова невозможно, запрос не должен бесконечно повторяться вслепую.

Такая ситуация требует reconciliation или ручного разбора.

### Обработка неопределённого результата

Если запрос на создание доставки завершился по timeout, платформа не переводит `DeliveryAttempt` в `FAILED` автоматически.

Возможны две ситуации: Carrier не получил запрос либо получил его и создал доставку, но ответ потерялся.

Алгоритм обработки:

1. Платформа сохраняет информацию о timeout и оставляет `DeliveryAttempt` в состоянии `PENDING`.
2. Если Carrier поддерживает идемпотентное создание доставки, платформа может повторить запрос с тем же `deliveryAttemptId` в качестве ключа идемпотентности.
3. Если Carrier предоставляет API проверки результата, платформа пытается установить фактическое состояние предыдущей операции.
4. Если достоверно подтверждено, что доставка не создана и попытка не может быть продолжена, `DeliveryAttempt` переводится в `FAILED`.
5. Если подтверждено успешное создание доставки, платформа сохраняет `carrierDeliveryId` и переводит `DeliveryAttempt` в `ACCEPTED`.
6. Если результат установить невозможно, автоматическое переключение Carrier запрещается. Соответствующее задание переводится в `BLOCKED` для последующего reconciliation или ручного разбора.

Отсутствие доставки в ответе поискового API Carrier само по себе не считается окончательным подтверждением отказа, если данные перевозчика обновляются с задержкой.

Новый `DeliveryAttempt` через альтернативного Carrier допускается только после исключения риска существования неподтверждённой доставки у предыдущего перевозчика.

### Конкурентная отмена во время создания доставки

Если пользователь запрашивает отмену Delivery во время её оформления у Carrier, необходимо учитывать состояние внутреннего задания `delivery_creation_jobs`.

**Задание ещё не выполняется:**

Платформа атомарно блокирует запуск задания, устанавливает статус Delivery `CANCELLED` и сохраняет изменение состояния вместе с событием в Transactional Outbox.

**Задание уже выполняется:**

Платформа сохраняет `cancelRequestedAt` и возвращает клиенту `202 Accepted`.

Фоновый обработчик проверяет наличие запроса отмены перед обращением к Carrier. Однако такая проверка не исключает ситуации, когда отмена поступает одновременно с отправкой внешнего запроса.

Поэтому после получения ответа Carrier обработчик повторно проверяет наличие `cancelRequestedAt`.

Возможные результаты:

1. Если создание доставки ещё не выполнялось у Carrier, платформа прекращает оформление и переводит Delivery в `CANCELLED`.
2. Если Carrier подтвердил создание доставки, платформа инициирует её отмену через Carrier API.
3. Если результат создания неизвестен из-за timeout, сначала выполняется reconciliation. До выяснения результата Delivery не переводится в `CANCELLED`.
4. Если Carrier подтвердил отмену, платформа устанавливает `CANCELLED` и очищает признак ожидающей отмены.
5. Если Carrier сообщает, что обычная отмена больше невозможна, платформа сохраняет актуальное состояние Delivery, очищает `cancelRequestedAt` и завершает ожидание отмены. `cancellationPending` становится `false`. Если Shipment уже передан перевозчику, дальнейшая обработка выполняется через сценарий возврата.

После получения окончательного результата операции признак ожидающей отмены не должен оставаться установленным.

`cancellationPending = true` используется только пока результат запроса на отмену остаётся неопределённым.

Запрос пользователя на отмену не должен приводить к повторному созданию DeliveryAttempt или дополнительной физической доставке.

При подтверждённом изменении статуса публикуется `DeliveryStatusChanged`.

## 6. Timeout

Все синхронные вызовы внешних Carrier API должны иметь ограничение времени ожидания.

Платформа не должна бесконечно ожидать ответ внешнего сервиса.

Высокоуровнево:

```text
Delivery Orchestration
        |
        | request
        v
Carrier
        |
      timeout
        |
        v
обработка временной ошибки
```

Конкретные значения timeout определяются на основании:

- SLA Carrier;
- допустимого времени ответа пользовательского сценария;
- статистики реальных задержек.

Фиксированное значение timeout в рамках текущего System Design не задаётся.

---

## 7. Retry

Retry используется только для ошибок, которые потенциально могут исчезнуть при повторной попытке.

### Retry возможен для

```text
timeout
HTTP 429 Too Many Requests
HTTP 5xx
временная недоступность сети
```

### Retry не выполняется для

```text
400 Bad Request
некорректного адреса
превышения допустимого веса
неподдерживаемого типа груза
других бизнес-ограничений Carrier
```

Повтор одного и того же некорректного запроса не изменит результат.

---

## 8. Retry policy

Повторные запросы не должны выполняться сразу один за другим.

Используется:

```text
exponential backoff
```

Например:

```text
первая ошибка
    ↓
небольшая задержка
    ↓
retry
    ↓
увеличенная задержка
    ↓
retry
```

Для снижения риска одновременных повторных запросов от большого количества instances может использоваться:

```text
jitter
```

Конкретное количество попыток и интервалы определяются эксплуатационными требованиями и характеристиками конкретного Carrier.

## 9. DeliveryAttempt и ошибки Carrier

Каждая попытка создания доставки у конкретного Carrier хранится отдельно в:

```text
DeliveryAttempt
```

Пример обработки неопределённого результата:

```text
Delivery
   |
   +-- DeliveryAttempt #1
          Carrier A
          PENDING
          |
          v
       TIMEOUT
          |
          v
       Reconciliation
          |
          +-- Доставка создана → ACCEPTED
          |
          +-- Подтверждён отказ → FAILED
          |
          +-- Результат неизвестен → BLOCKED job
```
Это позволяет:

- не перезаписывать историю предыдущих попыток;
- сохранять `carrierDeliveryId` отдельно для каждого Carrier;
- анализировать причины отказов;
- переключаться между Carrier;
- выполнять аудит.

## 10. Переключение Carrier

Если текущий Carrier не смог принять доставку, Delivery Orchestration может создать новый `DeliveryAttempt`.

Пример:

```text
Delivery
    |
    v
DeliveryAttempt #1
Carrier A
FAILED
    |
    v
поиск альтернативы
    |
    v
DeliveryAttempt #2
Carrier B
ACCEPTED
```
Автоматическое переключение Carrier запрещено при неопределённом результате предыдущей попытки создания доставки. Перед переключением платформа должна подтвердить, что предыдущий Carrier не выполняет доставку данного Shipment.

Автоматическое переключение разрешено только если сохраняются согласованные с пользователем условия:

- тип доставки не изменяется;
- стоимость для пользователя не увеличивается;
- срок доставки остаётся в согласованном диапазоне;
- ограничения Shipment выполняются.

Если для продолжения необходимо изменить стоимость, срок или выбранный ПВЗ, автоматическое переключение не выполняется.

Требуется повторное подтверждение условий пользователем.

---

## 11. DLQ

Если Kafka-событие не удаётся успешно обработать после допустимого количества повторных попыток, оно помещается в:

```text
Dead Letter Queue
```

Например:

```text
delivery.order-ready.dlq
```

DLQ позволяет не блокировать обработку остальных событий из-за одного проблемного сообщения.

Для сообщения в DLQ необходимо сохранять как минимум:

| Поле | Описание |
|---|---|
| `eventId` | Идентификатор исходного события |
| `eventType` | Тип события |
| `payload` | Исходное сообщение |
| `failureReason` | Последняя причина ошибки |
| `retryCount` | Количество попыток обработки |
| `failedAt` | Время помещения сообщения в DLQ |

Сообщения из DLQ должны быть доступны для анализа и повторной обработки после устранения причины ошибки.

## 12. Ошибки при изменении статуса Delivery

Carrier может повторно отправить один и тот же webhook.

Например:

```text
IN_TRANSIT
IN_TRANSIT
```

Повторное сообщение не должно повторно изменять Delivery и генерировать лишние события.

Кроме того, внешние события могут прийти не в ожидаемом порядке.

Например:

```text
DELIVERED
```

а позже из-за задержки:

```text
IN_TRANSIT
```

Delivery Orchestration не должна выполнять переход:

```text
DELIVERED → IN_TRANSIT
```

если он запрещён внутренней state machine.

Перед изменением состояния платформа проверяет:

```text
currentStatus + incomingStatus
            ↓
      allowed transition?
```

Если переход недопустим, состояние Delivery не изменяется, а ситуация логируется для дальнейшего анализа.

## 13. Атомарность изменения БД и публикации события

Рассмотрим сценарий:

```text
Delivery.status = IN_TRANSIT
```

сохранён в БД, после чего платформа должна отправить:

```text
DeliveryStatusChanged
```

Возможен сбой:

```text
UPDATE Delivery
        ↓
успешно
        ↓
приложение падает
        ↓
Kafka event не опубликован
```

В результате БД и Kafka окажутся несогласованы.

Для решения используется:

```text
Transactional Outbox Pattern
```

---

## 14. Transactional Outbox

Изменение Delivery и создание записи для будущего события выполняются в одной локальной транзакции БД.

```text
BEGIN TRANSACTION

UPDATE Delivery
status = IN_TRANSIT

INSERT INTO outbox
DeliveryStatusChanged

COMMIT
```

После commit отдельный publisher отправляет запись из `outbox` в Kafka.

```text
Database
   |
   | outbox
   v
Outbox Publisher
   |
   v
Kafka
```

Если публикация не удалась, запись остаётся в outbox и может быть отправлена повторно.

Такой подход снижает риск ситуации:

```text
данные изменились,
но событие потерялось
```

Consumer при этом всё равно должен оставаться идемпотентным, потому что Outbox Publisher может отправить одно сообщение повторно.

## 15. Circuit Breaker

Если конкретный Carrier длительное время недоступен, бессмысленно продолжать отправлять ему каждый новый запрос.

Для защиты платформы может использоваться:

```text
Circuit Breaker
```

Упрощённо:

```text
Carrier работает
    ↓
CLOSED

много последовательных ошибок
    ↓
OPEN

запросы временно не отправляются
    ↓
через некоторое время
HALF_OPEN

тестовый запрос
    ↓
успешно → CLOSED
ошибка   → OPEN
```

Это позволяет быстрее исключить явно недоступного Carrier из текущего процесса выбора.

## 16. Частичная недоступность Carrier

Недоступность одного Carrier не должна автоматически означать недоступность всей Delivery Orchestration Platform.

Например:

```text
Carrier A → timeout
Carrier B → отвечает
Carrier C → отвечает
```

Если Carrier B и Carrier C могут выполнить доставку, платформа продолжает работу с доступными вариантами.

Если ни одного Carrier невозможно проверить из-за технической недоступности, операция может завершиться:

```text
503 Service Unavailable
```

Важно отличать:

```text
вариантов доставки нет
```

от:

```text
невозможно определить доступные варианты
```

## 17. Reconciliation

Для обнаружения рассинхронизаций может использоваться периодический reconciliation-процесс.

Например, он может находить Delivery, которые длительное время находятся в промежуточном состоянии:

```text
CREATED
ACCEPTED
IN_TRANSIT
```

и проверять их состояние у Carrier.

Reconciliation используется как дополнительный механизм восстановления, а не как основной способ получения статусов.

## 18. Основные сценарии отказа

| Сценарий | Решение |
|---|---|
| Kafka доставила событие повторно | Idempotency по `eventId` |
| Для одного Shipment пришли два разных события | Бизнес-инвариант и уникальное ограничение |
| Carrier временно недоступен | Timeout + Retry |
| Carrier долго недоступен | Circuit Breaker / другой Carrier |
| Carrier вернул бизнес-ошибку | Retry не выполняется |
| Carrier создал доставку, но ответ потерялся | Idempotency Key / проверка результата |
| Событие невозможно обработать | DLQ |
| Webhook пришёл повторно | Идемпотентная обработка |
| Статус Carrier пришёл не по порядку | Проверка state machine |
| БД обновлена, но событие Kafka не отправлено | Transactional Outbox |
| Состояние Delivery долго не меняется | Reconciliation |
